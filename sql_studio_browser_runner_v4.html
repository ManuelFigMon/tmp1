Why a browser cannot reach SQL Server on its own

                    

                        SQL Server speaks the TDS protocol over a raw TCP socket on port 1433. Browser JavaScript has no raw TCP socket API — only HTTP(S), WebSocket and WebRTC. Integrated Security (SSPI / NTLM) also needs OS-level credential delegation that a sandboxed page is never granted. No JavaScript in this file can connect directly. Earlier versions returned canned rows from a keyword lookup, which is why editing the SQL appeared to do nothing.
                    

                


                

                    
Mode 1 — Local Engine (default)

                    

                        v4 ships a real SQL expression engine. It tokenizes and evaluates your statement rather than matching keywords, so the result always reflects what you typed:
                    

                    
SELECT 'Hello test World' AS Greetingssss;
  --> one column named  Greetingssss
  --> one row  containing  Hello test World

SELECT 40 + 2 AS Arithmetic, UPPER('abc') AS U;
  --> Arithmetic = 42,  U = ABC

                    

                        Supported: string/number literals, + - * /, string concatenation, comparison and AND/OR/NOT, CURRENT_TIMESTAMP, GETDATE(), DB_NAME(), HOST_NAME(), SUSER_NAME(), @@VERSION, LEN, UPPER, LOWER, CONCAT, ISNULL, plus SELECT [TOP n] … FROM … WHERE … ORDER BY against the tables in MOCK_TABLES. Unaliased expressions are named (No column name), matching SQL Server.
                    

                


                

                    
Mode 2 — API Bridge (live database)

                    

                        To run against the real server, start the companion bridge on a machine that can reach it, then set EXECUTION_MODE: "api".
                    

                    
npm install express mssql cors
node sql_studio_api_bridge.js

# then in APP_CONFIG:
EXECUTION_MODE: "api",
API_ENDPOINT:   "http://localhost:8787/query"

                    

                        The bridge receives {sql, host, port, database, auth} and must return {columns:[…], rows:[…]} or {error:"…"}. Use Test Bridge Connection in the left pane to verify it is reachable before running a query.
                    

                


                

                    
Cache handling

                    
    
                        
  • The page sends no-store, no-cache, must-revalidate plus Pragma and Expires headers.
    • 
                        
  • Every bridge call uses cache: 'no-store' and a unique _cb= parameter, so no response is ever reused.
    • 
                        
  • The previous result set is flushed at the start of every run, so a failed query can never leave stale rows on screen.
    • 
                        
  • Clear Cache & Reload empties sessionStorage, localStorage and the Cache Storage API, then hard-reloads with a cache-busting parameter.
    • 
                        
  • The footer shows a build stamp so you can confirm which copy is loaded.
    •
